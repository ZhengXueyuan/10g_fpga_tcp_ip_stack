`D:\repo\XCKU5PMini`（**不是 git 仓库**）= 厂商原始资料包。器件 **`xcku5p-ffvb676-1-e`**
（Kintex UltraScale+，**speed grade -1**，扩展温度）：16 GTY（quad 224/225/226/227）、
**2× SFP28**（底板）、1× **RTL8211E RGMII 千兆**、DDR4、PCIe Gen3 x4、QSPI 自启动。
资源：**BRAM 139/480、URAM 0/64（18 Mb 全空）**、LUT 15%。

它正在成为 **P6（10G）的换板候选** —— K7 上的四条硬伤（GT refclk 要焊接换晶振 / fabric 必须跑 322MHz /
评估级 license / 大窗要 DDR3）中**三条在 KU5P 上直接消失**：GTY 内建 64b/66b（
fabric 接口是 **64bit @156.25MHz**，322MHz 在 US+ 上不存在）、
`xxv_ethernet`/`ethernet_1_10_25g` 的 **standalone BASE-R PCS/PMA 据 component.xml 免费无 key**
（MAC 仍收费，但 MIT 的 `verilog-ethernet` 在 US+ 上有 KU15P 例程可用）、**URAM 18 Mb 全空**。
规格见 `C:\Users\zhxue\.claude\plans\p6_spec.md`。

**三条最贵的事实**（**已回填进该仓库的 `AGENTS.md`/`CLAUDE.md`**）：
1. **GT 参考钟晶振（丝印位号 Y2）实物已换成 156.25 MHz** → 网络 `MGT225_CLK0_P/N` → ball
   **`V7/V6` = `MGTREFCLK0_225`**；而**两条 SFP28 都在 quad 225**（SFP A=ch0：TX AA5/AA4、
   RX Y2/Y1；SFP B=ch1：TX W5/W4、RX V2/V1）⇒ **喂对了口子**。`156.25 × 66 = 10.3125 GHz` ✓；
   而出厂 100 MHz 只能 `100 × 103 = 10.3 GHz`（非标）⇒ **不换晶振这块板做不了 10GBASE-R**。
   ⚠️ **XDC 里的 `Y2` 是 ball 编号（= SFP A 的 RX+），与晶振位号 Y2 不是一回事**，同一份 XDC 里相邻出现。
   副作用：`Demo/` 两个预置位流按 100MHz 生成 ⇒ 换晶振后 **Aurora 锁不上**（RGMII 以太网不受影响）。
2. **板上没有 UART**（查遍用户手册全文 / 底板 5 页 + 核心板 7 页原理图 / Demo 用户 RTL / `资料/调试工具/`）。
   手册第 4 页说的"PCI 串行端口"是 **XDMA 的 class code `0x070001`（16550 兼容）**被 Windows 枚举出的
   **虚拟设备，不对应任何引脚**。⇒ **用户已决定（2026-09-27）：板级调试走 PCIe/XDMA**
   （状态/命令经 XDMA 寄存器或内存映射暴露；"前置闸"也走同一通道。
   ⚠️ XDMA 驱动无微软签名 ⇒ 要 `Bcdedit -set TESTSIGNING ON` + 重启）。
3. ~~本机 Vivado 2025.2 未安装 UltraScale+ 器件数据~~ —— **✅ 已解决（2026-09-28 复测）**：
   用户装上了 `kintexuplus` 器件包，`get_parts xcku5p*` 返回 **36 个器件**、FAMILY `kintexuplus`、
   含 **`xcku5p-ffvb676-1-e`**（我们的板子）⇒ **本机现在能对 KU5P 综合/实现/配 IBERT**。
   （当年症状：`get_parts` 返回 `<NO MATCH>`、IBERT 报 `[Labtoolstcl 27-3316] Cannot configure the GTs
   of this unsupported device`。**烧位流一直不受影响**，IDCODE `0x04A62093`。）
   ⇒ **闸 F（HLS 新器件收敛探针）、闸 G（KU5P 时序基线）现在都可以开工了。**

**4. 10G 物理层已实测通过（2026-09-27，iBERT + AOC 外部环回）**：
- **QPLL0 锁定在 `FBDIV=66 × 156.25 MHz = 10.3125 GHz` 整** ⇒ ⚠️ 若 Y2 仍是 100 MHz，
  `66 × 100 = 6.6 GHz` **低于 QPLL0 的 9.8 GHz VCO 下限、根本锁不上** ⇒ **"锁上了"本身就证明晶振确已换对**。
- **外部环回（SFP A ↔ SFP B 经 AOC）双向各 1.239 Tbit 零错误、合计 4.3×10¹² bit**
  ⇒ **BER < 2.4×10⁻¹²，优于 10GBASE-R 的 1e-12 要求**；未接线缆的通道同时仍是 0.5（完美对照）。
  独立复核：累计 BER 稀释 + `ERRBIT=243` 反解吻合 ⇒ 243 个错误全在链路建立瞬态。
- 眼图 @1e-5：水平 **0.52 UI** / 垂直 **80.6%**；相对内部环回代价 = 水平眼少 **0.25 UI**
  （⚠️ 但那是**整条外部路径**的总代价，含两个 SFP 模块与 AOC，**连接器无法单独拆出来**）。
- 手册"12 GHz"那句：与数据一致（10.3125 < 12），但**本轮没触及 12 GHz 边界**，不能说被验证或推翻。
- ⚠️ **没测到真正的 64b/66b PCS**：iBERT 经 Tcl 只能选 `Custom`，`DATAWIDTH` 硬钳 80、
  `TXGEARBOX_EN=FALSE` ⇒ **GT 跑 raw**。线速率/UI/Nyquist 与 10GBASE-R 一致 ⇒ SI 结论成立，gearbox 未跑到。

**5. 10G IP 许可（2026-09-27 判定）**：`xxv_ethernet` 的「standalone BASE-R **免费**」是**文档级承诺、
license manager 未实现** —— `component.xml` 整个组件**只有一个 licenseKeys 块、无按配置映射**
（实测：把 `Xilinx.lic` 改名后，PCS/PMA-only 与 MAC 配置**一样被锁、无法区分**）。
**⇒ PCS/PMA-only 照样消耗 `xxv_eth_mac_pcs` 等 key，不存在免 key 通道。**
**但本机不需要买** —— 三个 key 已随安装捆绑在 `core_licenses/Xilinx.lic`（全 `Design_Linking`）。
**位流实测（2026-09-27）**：该配置出流成功（15,431,263 B）**但 bitgen 逐字打印 `[Vivado 12-1790]`
并点名三个 `design_linking` feature**；判别力已建立（同流程的**无 IP 平凡设计出现 0 次**）。
⚠️ 但不能排除"警告部分是 blanket"（点名的 feature 本配置都没用；AMD 对 `cmac_usplus` 有"不用可忽略"口径），
且**超时会不会发生/多久未上板实测** ⇒ **按"会超时"准备：量产要买那三个 key**；
也正因如此，**MIT 开源栈（`verilog-ethernet` + 免费 `gtwizard_ultrascale`）成了有竞争力的量产选项**。
⚠️ **连带纪律**：长时板级测试要加**存活探针**并把"跑到一半死掉"识别为*超时*而非*设计 bug*；
`_bitgen\nc\nc_plain.bit`（无 IP、永不超时）可作同板同线对照位流。

**8. ✅ 1G 以太网 MDIO 板级打通（2026-09-28）—— 工程 `_proj_mdio/`**：
- 做法：**VIO 当 JTAG 寄存器窗口**（板上无 UART；XDMA 太重），RTL = VIO 驱动的 Clause-22
  MDIO 主机（`rtl/mdio_master.v` + `mdio_vio_top.v`），主机侧 `probe_phy.tcl` 驱动并扫描。
  坑见 [[vio-over-jtag-gotchas]]（五个 API 陷阱，每个症状都是"完全不通"）。
- **实测结果**：**PHY ID = `0x001CC915` = RTL8211E 标准 ID** ✓。
  同时证明 `T25/U25` 100MHz 时钟在跑、`eth_mdc=G10`/`eth_mdio=B9`/`eth_rstn=A9` 映射正确、
  MDIO 主控在真硅上功能正确。负对照：地址 2–31 全 `0xFFFF`（总线被上拉）。
- ⚠️ **待查**：**地址 0 与 1 都应答同一 ID**。按理每个 PHY 只应答一个地址
  （RTL8211E 由 `E_RXCTL/PHY_AD` 脚搭接）。2–31 的 `0xFFFF` 已排除"读到陈旧数据"。
- ⚠️ **RGMII 15 个引脚目前只有 MDIO 三个（G10/B9/A9）经过了硬件验证**；数据面
  （`i_rxc`/`o_txc`/8 根数据/2 根控）还只是"图纸 + 厂商 XDC 两路互证"，**未上板**。

**9. ⭐ RGMII 前端在 KU5P 上的正确配方（2026-09-28 P6a-T2 实证，**推翻"IDELAYE2→E3"旧计划**）**：
- ① **KU5P 的 RGMII/MDIO 全在 bank 86 = HDIO（High Density I/O）** —— 不是 HP。
  **HDIO 不支持 I/ODELAY，也不支持 ISERDES/OSERDES、没有 BUFIO/BUFR**（厂商 KU5P 设计的
  `BUFIO` 被综合降级成 `BUFGCE` 就是证据）。**实证**：`board/ku5p_probe/idly_probe.v`
  （IBUF+BUFG+MMCME4+IDELAYCTRL+IDELAYE3+IDDRE1+ODDRE1 挂真实 RGMII 引脚）综合过、opt 过，
  `place_design` 报 **`ERROR: [DRC PLHDIO-6] ... the shape contains IDelay and ISerDes
  (details: presence of I/ODELAY or I/OSERDES is not supported in HDIO)`**。
  ⇒ **`IDELAYE2→IDELAYE3` 这条路在这块板上物理不成立**；`IDELAYCTRL` 与 300MHz 参考钟一并消失。
- ② **底板把 PHY 的两个 RGMII 延迟搭接都拉高了**（原理图出图实测，PDF 文本层错位不可信）：
  `LED2/RXDLY`(pin32) → **R52 10k → VDD3.3** ⇒ **RXDLY=1**（PHY 给 RXC 加 ~2ns）；
  `RXD[1]/TXDLY`(pin16) → **R51 10k → VDD3.3** ⇒ **TXDLY=1**（PHY 内部延迟 TXC 去锁 TXD）。
  ⇒ **FPGA 侧正确做法 = 零延迟**：RX = `IBUF→BUFG→IDDRE1`（C/CB 同网 + `IS_CB_INVERTED=1`，
  `SAME_EDGE_PIPELINED`，Q1=低 nibble@上升沿）；TX = `ODDRE1` 边沿对齐驱动
  （D1=低 nibble / D2=高 nibble，**同一个已寄存字节**）。**不需要 IDELAY / IDELAYCTRL / MMCM**。
  顺带：原理图注记 **`PHY_ADDR[2:0]=001`** ⇒ PHY 地址 1（与 MDIO 实测地址 1 应答吻合）。
- ③ **K7 的前端配方不可移植，但 TX 配方本身是自洽的**：已实现并验证
  `board/util_gmii_to_rgmii_us.v`（零 IDELAY 版）+ 判据 `tb/tb_rgmii_phy_model.v`
  （行为级 RTL8211E 模型：RXDLY=1/TXDLY=1，往返逐字节一致 + 唯一位移）：
  **KU5P 前端 TX/RX 各 200/200 字节 d=0 全对**；**K7 前端 TX 也全对**（`gmii_txd_low` 是
  **阻塞赋值读沿前 `gmii_txd_r`**、天然多滞后一拍，正好补偿 `gmii_txd_r_d1` 的两级流水 ——
  手算容易在这里算错），但 **K7 的 RX 在 RXDLY=1 的 PHY 上 mis=179 全错** ⇒
  **ECO 板的 PHY 必然是 RXDLY=0**（K7 靠 `IDELAYE2`+`BUFG(~rxc)` 自己凑相位）。
- 构建产物：`_proj_mdio/pj_mdio/.../mdio_vio_top.bit`（15,431,263 B，**WNS +7.091 / WHS +0.020**）。
  ⚠️ 该 WNS **不是** KU5P 的时序基线（设计太简单）；真正的基线要等 64 位数据面。
- ⚠️ **纪律**：烧录只走 JTAG，**绝不写板载 QSPI** —— 那里存着厂商的 XDMA+DDR4 设计
  （经查磁盘上 `Demo/.../DDR_PCIE_ETH_SFP_TOP.bit` 可作恢复源）。烧上我们的位流后
  PCIe 端点会消失，而 **Z87 根端口不发热插拔事件** ⇒ `lspci` 会留陈旧条目，
  要 `remove`+`rescan` 才消失（配置空间读 `ffffffff` 即可判死）。

## ✅ 2026-09-29: P6a 收口 + 我们自己的 PCIe 观测通道上板可用

- ⭐ **观测通道 = 自己的 PCIe 寄存器窗口** (`P6E_OBS.md` 是操作手册)：数据面 → `snap_cdc`

  (ping 那一轮就是靠它把断点定位到"帧进了慢路径但 HLS 没回")。当前 16 字快照, `BUILD_ID` 自增认版本。
- ⚠️ **烧录纪律修正**(实测, 比上面那条更准): 烧**带 PCIe 的设计**之后, 链路会重训因而端点仍在,
  但 **AXI 通路要等重启才活** ⇒ 判"能不能用"**只能看 BAR 打不打得动**;
  `lspci` 有条目、甚至 config 空间读得出 `10ee:9034` **都不算证据**(可能是主机侧缓存)。
  判别器 `_proj_pcie/p6e_precheck.sh`(control vs user 两个 BAR 一起看)。
- 板子身份: IP `192.168.100.2` / MAC `00:0A:35:01:FE:C0`; 对端 `192.168.100.1/24` 加在
  直连板子的那块网卡上(本机是 `enp3s0`, SSH 走 WiFi 互不影响)。
- ✅ **2026-09-29 图案/吞吐: 931 Mbps = 1G 线速** (板子自报 79,069 帧/s × 1472B;
  网卡硬件计数 78,917 帧/s 独立互证到 0.2%), 收到的帧**逐字节**等于 xorshift64 图案流连续前缀,

  会把"自己接收侧的天花板"误读成"板子慢"(我一度因此推断"背靠背无 IFG", 查 mac_tx_64 FSM 后否掉)。
  ⚠️ 快照寄存器是**冻结到下次触发**的语义 ⇒ 任何采样脚本**每次读之前都要写 0x18=1**,

## ✅ 2026-09-29 同日续: P6b —— 数据面搬到 **156.25MHz** 并板级正式验收通过 (35/35)

**一页式总览 = `udp_hls_10g/P6B_SUMMARY.md`（接手先读它）；验收原件 = `P6B_ACCEPT.md`。**

- **架构**：前端（RGMII + `mac_rx_64`/`mac_tx_64`）留 **125MHz**（`i_rxc` 是 PHY 回送的，不该改）；
  其余全部搬到独立自由运行的 **`dp_clk = 156.25MHz`**（核心板 Y1 100MHz 经 MMCM ×1.5625）；
  两者之间只有**两个**异步边界（`rtl/fifo_async.v`，手写灰码指针）。
- **板级实测**：**数据面 156.2409/156.2419 MHz**、**前端 125.0061 MHz**（同一次测量里两域频率分开读出
  = "真搬过去了"的硬证据）；**956.0 Mbps = 该帧长线速上限 957.1 的 99.9%**（P6b 前是 931 —— 
  **提频把 DP 自身的处理节拍瓶颈消掉了**，这是可测量的收益）。
- ⭐ **MMCM 输入差分标准的裁决（与厂商 XDC 相悖，实测被硬件接受）**：板上是 0.1µF 交流耦合 + 1k/1k
  分压到 VDD1.2 ⇒ 共模 **0.600V = VCCO/2** ⇒ 用 **`DIFF_SSTL12`**（ds922 Table 14 的 typ）
  而**不是**厂商 XDC 写的 `DIFF_POD12_DCI`（Table 15 的 VICM 下限 0.76V，0.600 低于下限）。
  **反方证据如实保留**：厂商位流的 MIG `sys_clk` 就是这对脚且实测跑通。退路 = 一行改回。
  引脚事实：`T25`=`IO_L14P_T2L_N2_GC_A04_D20_65`，bank65(HP)，时钟区 X0Y1 有 MMCM；
  Y1 = **100.000 MHz**（原理图/MIG xci/XDC 三源互证）。
- **两个早于 P6b 就存在的真实缺陷被本轮仪表照出来并修掉**（都属"计数器报成功而数据其实坏了"）：
  **F4**（RX 帧尾用**寄存器化的 `full`** 判空间 ⇒ TLAST 字被静默丢弃）；
  **F-2**（TX 帧内中止后残字被当新帧发出 ⇒ 线上出现 **FCS 完全正确**的幽灵帧）。
