### 2.2 独立模型 M1：锁序全枚举 ⇒ 回绕的**充要刻画**（我自建，未跑 kimi 脚本）

模型：两线程各一对临界区 `S`（snap）/`C`（commit）；约束 = 锁互斥（点事件下的线性全序）+ 线程内程序序 `S<C`；`w70` 单调递增；`rl` 初值 = 前一条 commit 基线。**关键修正**：`S` 的值必须**按时间序**赋值（先 `S` 读 `v_lo`，后 `S` 读 `v_hi ≥ v_lo`）——kimi 手推的数值关系依赖于此。

`bx_race_model.py` M1 输出（见 `OUT_race_model.txt`）：

```
        A1 A2 B1 B2          ⇒ A2:dw=0  B2:dw=500
        A1 B1 A2 B2          ⇒ A2:dw=0  B2:dw=500
  WRAP  A1 B1 B2 A2          ⇒ B2:dw=500  A2:dw=4294966796(WRAP)
  WRAP  B1 A1 A2 B2          ⇒ A2:dw=500  B2:dw=4294966796(WRAP)
        B1 A1 B2 A2          ⇒ B2:dw=0  A2:dw=500
        B1 B2 A1 A2          ⇒ B2:dw=0  A2:dw=500
⇒ 可行锁序 6 种；回绕序 = 2 种: ['A1 B1 B2 A2', 'B1 A1 A2 B2']
```

**定理（我的刻画）**：在两线程各一对 `[S,C]` 窗且 `v_hi > v_lo`（两 S 之间 ≥1 字节丢事件）的条件下——
**回绕 ⟺ 两线程的 `S` 先后与 `C` 先后相反 ⟺ 一个线程的 `[S,C]` 窗完整嵌套住另一个线程的 `[S,C]` 窗**。
- kimi 的确定性交错（`A snap(1000) → B snap(1500) → B commit → A commit`）**恰是嵌套序之一**（`A1 B1 B2 A2`），其算术 `A 行 = 0xFFFFFE0C = 4294966796` **逐位复现** ✓；我补充了**镜像序** `B1 A1 A2 B2`（此前 kimi 的 .md 只写了单向）。
- 嵌套序下：回绕行打印 `2^32 − δ`（δ = 两 S 间的丢量），**并且** `rl_w70` 被回写为旧值 ⇒ 下一条 commit 会**多计 δ**（账目在两行间"搬运"，总量失真恰 +2^32/事件）。
- 非嵌套序（含 `A1 B1 A2 B2` 这类"交错但不嵌套"）**保证零回绕**——这解释了为什么真机常见交错（见 2.4 的 t 序交替）却 0 回绕。

### 2.3 频率类数字：kimi 的 186,170 是模型产物（不是真机频率上界的一部分）

- kimi 的随机模型（`xreview_b_verify.py` V2）把两线程全部 `snap/commit` **自由洗牌**，仅以 FIFO 保证"commit 消费本条自己的 snap"——**允许 `commit_k` 漂移到 `snap_{k+1}` 之后**（真代码不可能：线程在 `S_k→C_k` 后要做下一笔 read 才到 `S_{k+1}`），且无锁/无时序/无相位。⇒ 其 `186,170/800,000 ≈ 23.3%` 只是该模型的属性。
- 我的 M2（**显式强制**线程内 `S_k<C_k<S_{k+1}`，op 原子、两窗任意重叠）：**16.3%**（每线程 8 行 × 20,000 次 = 320,000 行，回绕 52,180 行；`OUT_race_model.txt` 逐字）。同为"自由重叠"假设，说明数字强烈依赖模型设定 ⇒ **两者都不可当真机频率引用**。
- 我的 M3（相位分离形态模型；参数 = 假设）：`p_ov=0 → 0.000%`；`0.005 → 0.004%`；`0.02 → 0.029%`；`0.1 → 0.162%`。**只用于说明"相位重叠是唯一触发条件"**，不是测量。
- **真机形态的独立推断（证据链 = 驱动只读源码，我已逐行抽查，见 §3-P2 附注）**：`xdma_xfer_submit` 持 `engine->desc_lock` 跨【建表→排队→等完成】（`runs/driver_libxdma.c`：`mutex_lock` :3553 → `transfer_init` :3560 → `transfer_queue` :3584 → 等完成 :3594-3600 → `mutex_unlock` :3680；解锁只在错误分支 :3562/:3586/:3676）⇒ **同一引擎任一时刻至多一笔 transfer**；两线程的 read 因此串行交替，各自的 readlog 块（~5 µs 级）在稳态下**相位相差一整块传输时间（实测 A1 相邻 commit 间隔 ≈11.5–11.8 ms；`mmio_us` 中位 = 5.0 µs）** ⇒ 嵌套需要**瞬态相位重合**（启动错拍/看门狗/停摆恢复等）。此推断**未做逐事件见证**（无逐行锁定序见证仪器），按"推断"读。

**机理（实例，A1 行 104/105/231）**：dual 的 rlog 是**按线程拼接**（`:1282-1286`：thread0 全表 → thread1 全表；`print_readlog` 头注 `:1372-1374` 只对 `gap_us` 声明了这一点）。打印序相邻两行常是**同一线程**的两条记录，而它们之间**全局 commit 序里夹着另一线程的 commit**——那条夹入的增量被记在**另一线程的行**上。实例：print#104（pc=876,609,536，w70=1,208,650,632，dw70=40,064）→ print#105（pc=884,998,144，w70=1,208,651,528，dw70=**0**）：打印邻差 = 896，但 896 被记在 print#**231**（t 序上位于 104 与 105 之间，pc=880,803,840，dw70=**896**）——按 t 排序后链完美闭合。

⇒ **结论**：口径句作为**算术陈述**（dw70 是该行与"上一条 commit"之间的增量）**在 t 序下逐行精确成立**（7 个 dual 窗 100%）；作为**打印表阅读指令**对 dual **不成立**（实测 50–98% 相邻对不满足）。REPORT 已登记的注释只说了"按线程分层/先分线程"——**不够**（同线程段内相邻行同样断链）；正确读法 = **按 `t` 排序**。而嵌套竞态是真机上打破 t 序链的唯一通路（未观测到）。
