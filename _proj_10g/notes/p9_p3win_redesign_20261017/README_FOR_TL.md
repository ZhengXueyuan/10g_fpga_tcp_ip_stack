## §0 三行结论

1. **Q1（构型能否达标）**：**能——但必须换一个机制族**。cfg A 失败的机理已由源码级时序链定死：**同一槽位的 ADD 事件（被动连接"乐观建连" ⇒ ADD 打在 SYN 处理拍，`hls/src/layer_tcp.cpp:668-679`）在因果序上恒晚于该槽的 DEL（→`ev_down`→app `closing`），而 app 的收尾只需 ~3 拍** ⇒ 事件到达时 app 只可能处于 **idle 或 closing**，**永远不可能处于"组装中"** ⇒ P-3 危险拍（帧首首载荷字装载拍）**在该族构型里结构性不可达**（0.070 的门不是"太小"，而是**模型把 closing 事件误当成组装事件**）。⇒ 设计 1 个可达标构型 **C1「静默释放槽位偷取环」**（零 RTL、纯对端参数 + ~150 行 sink delta）：**同槽存活事件 ≈ 11–12.5/s**（板侧 `T_SYN_RCVD` 超时**静默**释放活连接槽位，`hls/src/layer_tcp.cpp:532-535`，`TCP_RTO_MIN = 10,000,000` ≈ 80 ms，`layer_tcp.cpp:39-40`）⇒ 120 s ≈ **1,300 事件 × P≈5.0e-3 ⇒ 期望命中 ≈ 6.5（>3 ✓）**；300 s ⇒ ≈ 16。**前提 = 对端把连接"开了不关、持续读干"**。
2. **Q2（期望门公式）**：**应改**。三条：① **删 `ΔW74`**（异槽存活事件经 `up_pend` 路径，**结构性到不了装载拍**——设计件 §1.4(P-1) 自证；在 C1 构型里它占 ~2/3，公式会**虚高 ~3×**）；② 分子换 `ΔW52/ΔW5`（实测帧率/时基，直接是"每拍落装载拍"的频率，不经 `W51/1460` 两次换算）；③ **加一条构型侧前件**（"事件到达时 app 在组装"必须**结构性论证或直测**，不能由"alive"顶替）——这条是 cfg A 翻车的真原因。直接测 H1 分母的计数器（设计件 §1.4 的可选 `stat_p3_win_ev`）= **一次构建**，收益 = 把概率模型换成直读；但**它测不了 0x24 臂**（该代无此仪器）⇒ **列为备用刀，不是第一步**。
3. **Q3（收口路径）**：**"设计侧空判据 + I1 结构免疫"对"现役位流（0x28）的正确性"这一问是**够的**；对"P-3 类判据复资格 / S0C 形态解释 / 0x24 负对照资格"这三问不够**。I1 的承重件**现读核实齐**（`rtl/app_pattern.v:551/:548/:625` + 三处装配写 `:1003/:1024/:1034` + W1 支配监视器 + u_swc0/1 在旧 RTL 上**必红**的 xsim 正控——含"打第 1 帧=空判据、改打第 2 帧（位置=1460≠0）恢复判别力"这条已修正的定位法，`sim/p9_swc_gate/tb_p9_swc.v:154-176`）。**边界**：S0C 形态（`K0=37960 ∧ breaks=0`）至今**未定位**（设计件 v2 §7-1 自认"要得到 K0=37960 必须 raw ev_up 恰命中 1 拍装载窗（概率极低）或**事件路径另有洞**"）⇒ 设计侧收口**必须把这句原样挂进 OPEN_ITEMS**，不许读成"已解释"。**成本对比见 §4 表**；净建议 = **走 C1 一轮（~1 天，含工具 delta）**，设计侧收口作为"不做 C1 时的兜底口径"。

### 1.2 事件链的时序（逐拍，全部现读源码）

**关键前提（本轮新核，与设计件的"事件相位随帧"叙事不同）**：`ev_up` **不是**在建连握手完成时才发，而是**在 SYN 处理拍就发**——被动连接是"乐观建连"：`T_LISTEN` 分支在收到 SYN 的同一次 HLS pass 里就 `cfg_write(ADD)` + 发 SYN-ACK（`hls/src/layer_tcp.cpp:668-679`，注释逐字"乐观建连 — 把连接配置推给 fast path (CAM/TCB), 数据面直接可用"）；第三个 ACK 走 fast path ⇒ **HLS 永远停在 `T_SYN_RCVD`**（`:682-684` 注释逐字）。⇒ **`ev_up` 时刻 ≈ SYN 到达 + µs 级**，与"重连握手耗时 0.1–0.3 ms"无关。

**cfg A 一个连接周期（顺序连接，`--abort-rst` → 立即重连）**：

| # | 事件 | 时刻 | 机制（现读） |
|---|---|---|---|
| ① | sink 满 2 MB → `close()` 发 **RST**（`SO_LINGER{1,0}`） | t0 | sink 侧 |
| ② | 板收 RST → HLS `flags&TCP_RST` 支：`state=T_FREE` + `cfg_write(DEL)`（`layer_tcp.cpp:627-641`） | t0+µs | RST 帧 → SLOW（`rtl/rx_classify.v:110-118` 控制帧 ⇒ SLOW） |
| ③ | `slow_cfg_adp` 解析 DEL 记录（8 词）：`S_TCB` 的 `state=0` 落地拍发 **`ev_down`**（`rtl/slow_cfg_adp.v:166-167`） | t0+µs+~10 拍 | — |
| ④ | app：`ev_down ∧ active ∧ (ev_slot==act_id) ⇒ closing<=1`（`rtl/app_pattern.v:904-906`），**下一拍起 `asm_go=0`**（`asm_go` 含 `!closing`，`:625`） | ② +1 拍 | **"组装"到此终止** |
| ⑤ | W3 收尾：`pw_valid` 有字则带 tlast 交付、否则 0 载荷收尾字——**都要等 `m_tready`**（`:917-940`，`m_tready` = 下游 `axis_pipe`/帧器接受）；快流工况 `m_tready` 高 ⇒ **≤2–3 拍落 `active<=0`** | ② +2~3 拍 | 24 个"alive"事件量出的窗口 ≈ 3 拍（见 §1.3） |
| ⑥ | sink 侧 `socket()/connect()`（close→connect 间隙 = 代码路径）发 **SYN** | t0+δ′ | δ′ ≈ 数十 µs（由 §1.3 反解） |

| ⑧ | `slow_cfg_adp` 解析 ADD 记录（8 词 + `S_TCB` 六字段 + `S_TCB_LAST`）：**`ev_up` 脉冲**（`slow_cfg_adp.v:193-195`） | ⑦ + ~16 拍 | ⇒ **`ev_up` 恒晚于 `ev_down` ≥ ~26 拍**（DEL 记录 8 词 + `S_CAM` + `S_TCB` ≈11 拍 + ADD 解析 ≈16 拍；两记录同 FIFO 顺序解析） |
| ⑨ | app：`idle_now=1 ⇒ sw_apply=1 ⇒ 干净应用`（on 0x28；`:551`）——或 `closing` 未完成时 `ev_same_act ⇒ sw_req`（= 那 24 例） | — | — |

**⇒ 结构结论【已证（源码链）】**：**同一槽位的 `ev_up` 在因果序上必然晚于该槽的 `ev_down`（≥26 拍 + δ′）**；而 **`ev_down` 在 1–3 拍内就把 app 从"组装中"逐出（closing）** ⇒ **事件到达时 app 的可行状态集合 = {idle, closing}，不含"组装中"** ⇒ 危险拍（需 `active ∧ !closing ∧ !frm_wait ∧ !op_pend ∧ !pw_valid ∧ seg_sent==0`，设计件 §1.1 C1–C4）在该族**结构性不可达**。

### 1.3 那 24 个 "alive" 事件是 closing 事件（定量自洽）

- 若 app 收尾耗时 `ε_close` 拍、close→SYN 间隙 δ′：`P(alive) = ε_close/δ′`。
- 实测 `P(alive) = 24/36,809 = 6.52e-4` ⇒ 取 `ε_close ≈ 2–3 拍`（§1.2 ⑤ 的上界）⇒ **δ′ ≈ 4,600 拍 ≈ 30 µs**（与"sink close→connect 的代码路径"量级相符）【推断，自洽】。
- 且这 24 例到达拍上 `closing=1` ⇒ 即使碰撞也**无装配写**（C4 挡死）⇒ **其真实命中概率 = 0，而不是 `P = 2.914e-3`**。
- ⇒ **期望门的真实值 ≈ 0（不是 0.070）**；门与真值同向（都 < 3）但**差 1 个数量级的口径**：门说"再加 45 倍事件就够"（诱导"提高事件率"），真值说"加多少倍事件都是 0"（**必须换机制**）。**这是"构型重设计"而非"构型加料"的依据。**

### 1.4 与设计件 §2.1 预期（200–500 事件/s、期望命中 66）的差在哪

设计件把 H1 定义为"对端杀旧连接后板侧**不发 DEL / DEL 晚于 ADD**"。**"不发 DEL"这条在 RST 臂上被源码链否掉**（②③ 的 DEL 是 RST 的直接后果）；而"DEL 晚于 ADD"要求**事件路径另有洞**（= 设计件 v2 §7-1 亲口保留的那条）——本轮找到的洞 = **§2 的"静默释放槽位"**。事件率 306.7/s **在设计预期内**；塌的是 **alive-且-组装 的占比**。

## §2 Q1-B：候选构型（1 主推 + 2 变体）+ 期望门推算

### 2.0 共同机理：唯一可达"组装中 + 同槽"的路径 = **板侧静默释放活连接槽位**

**现已核**（全部 `hls/src/layer_tcp.cpp` 现读）：

- `TCP_RTO_MIN = 10000000`（`:39-40` 逐字注释 "~80ms min RTO"）、`TCP_RTO_MAX = 80000000`（`:42`）。
- RTO 扫描（`:513-535`）：`if(c.retrans_pending){ c.rto_timer++; if(c.rto_timer>=c.rto){ … if(c.state==T_SYN_RCVD){ **c.state=T_FREE; c.retrans_pending=false; continue; }** …}}`——**只释放槽位、不发 CFG_DEL**。
- `retrans_pending` 的武装：`tcp_send` 里 `flags&TCP_SYN ⇒ retrans_pending=true; rto_timer=0`（`:307`）；初值 `c.rto=TCP_RTO_MIN`（`:619`）。
- **活连接恒停在 `T_SYN_RCVD`**（乐观建连，第三 ACK 走 fast path）⇒ 该超时**对活连接照样触发**：**SYN-ACK 后 ~80 ms，槽位被静默释放，而 fast-path TCB 与 app 会话毫发无损**。
- `tcp_find` = 最低空闲槽（`:142-148`）⇒ 新连接的 SYN **会拿到这个"看似空闲、实则在服役"的槽**。
- 之后 `cfg_write(ADD)` 的 TCB 写会**覆盖该槽的 fast-path TCB**（`slow_cfg_adp.v:98-108`：`state=ESTAB` 等七字段）⇒ app 的 `tx_ok`（`rtl/app_ctrl.v:557-572`，`c_state==ESTAB ∧ 在飞<min(wnd,WIN_CAP)`）**在新 TCB 上立刻为真** ⇒ **app 的流无缝续到新连接**——这正是 S-0 轮"新连接首载荷 = 旧流位置续延"的观测形态。

**⇒ 构造的构型（C1）**：**一条长命连接保 app 组装（对端持续读干）+ 新连接洪流反复偷槽** ⇒ 每个"偷槽 ADD"落在 **app 组装中 + 同槽**，其相位与 app 帧循环**独立**（SYN 由对端独立进程发出）⇒ **设计件 §1.3 的均匀相位假设在该构型下才真正成立**。

### 2.2 C1 的施工规格（工具面，供 TL 排期用；**本件不实施**）

**sink delta（新件或新模式，建议同目录 `p7b_tcp_churn.cpp`）**：

1. 主循环 = `poll()` 多 fd（或 C1′ 的单 current fd）+ 一个 connect 定时器（`--connect-interval-ms`，默认 10）。
2. 连接建立：非阻塞 `connect()`（沿用 sink 件的 socket 建立序列 `:243-266`，含 `SO_RCVBUF` 落点）⇒ 加入读集合。
3. **永不主动关闭**；可选"安全关闭"规则：**仅当某个"更新"的连接已收到数据后**，才关旧 fd（证明槽的 4-tuple 记录已被覆盖 ⇒ 旧连接的 FIN/RST 不再匹配 ⇒ 不触发 `ev_down`；`layer_tcp.cpp:636` 的匹配语义）。
4. **读 + 判据**：每 fd 保留首 ~64 KB；**重启扫描**（见 §2.4 读数 A）：在前 ~4 KB 内搜 32 字节 `pattern[0..31]`（由 SEED 递推，`gen_byte=tx_lfsr[31:24]`；pattern[0]=0x9E）。
5. 报告：每连接一行 `CHURN conn=k bytes=… restart@off=? idle_ms=…`；**无 restart 的连接把首 64 KB 落盘**（供 §2.4 读数 B 离线复算）。
6. 部署纪律照旧：`p7b_affinity/BUILD.md` 配方 + md5 见证 + 五项自检；`ulimit -n ≥ 16384`（若不做安全关闭，120 s×100/s ≈ 12,000 fd）。

**臂脚本**：`p3churn` 臂 = 两代同参（0x28 / 0x24），**时长 120 s 起、300 s 最好**；快照 KW（0x28 臂）= `5 20 43 51 52 55 63 64 71 72 73 74`（E12 四字 = W71..W74，现读 `p9_build_0x28/p7b_ku5p_stdout.txt` 别名表 + `p9_build_0x28/EDITS_28_BLOCK.txt`）；0x24 臂无 E12（KW 按 0x24 几何，`NW=71`）。**pcap**：全帧 pcap 在 ≥3 Gbps 结构性追不上（P3 轮 §7-1 已证）⇒ **C1 的内容证据走 sink 内部扫描 + 落盘头**，不依赖 full pcap；ctl pcap 仍要（见证"板侧零控制帧"= 会话未被 DEL 的旁证）。

### 2.3 C1 的风险（逐条带可观测签）

| # | 风险 | 可观测签 |

### 2.4 读数设计（**这是 C1 与 cfg A 最大的工具面差别**）

- **读数 A（床内、零额外分析）："重启扫描"**。每偷槽连接的首 ~4 KB 内**是否出现 `pattern[0..]`（32 字节）**：
  - **出现在 ~1 帧内（≤2 KB）** ⇒ = 该事件走了"pending/干净"路（0x24 的 mid-frame pending 在下一帧界应用 ⇒ 重启；0x28 的 `sw_pend` 收尾后应用 ⇒ 重启）——**非命中**。
  - **首 ~4 KB 内不出现** ⇒ **命中候选**（= 覆盖写：SEED 被 `xs_next` 盖掉 ⇒ 流不断、不重启）。⚠️ 保守性：若同一连接内**后续**事件又产生 pending 并重启，会漏判（**下界**）；但"重启只可能发生在第一帧界"这一时序（pending 在**最近**的帧界应用，设计件 §1.4(P-1) 的证明）使该窗设置正当。
- **读数 B（离线、逐字节、权威）**：对 A 筛出的候选连接，用 **align 工具（现成 `align_check2.py` 语义）**复算 `K0 / breaks`——**注意扩头上限**：现工具的 `gen_pattern(0, 1<<22)` = 4 MB 头，而 C1 的流位置会远超 4 MB（连续流）⇒ **必须改成"从 SEED 递推到任意偏移"**（LFSR 递推是纯 CPU，GB 级偏移 = 秒级）⇒ 得出 `K0≠0 ∧ breaks==0`（= **0x24 的命中签**，设计件 §3 表）= **`K0≠0 ∧ breaks≥1`（pending/0x28 形态）** 的二值判别。
- **板侧读数（0x28 臂）**：前件 = `ΔW71 > 0`（应 ~3,900/120 s）∧ **`ΔW72 > 0`（应 ~1,300）** ∧ 三态恒等式闭合（`ΔW71 = ΔW73 + ΔW72 + ΔW74`——注意 `ΔW73` 含登记后应用，见 §3 ④）；P 的见证 = `ΔW52/ΔW5`；组装率见证 = `ΔW63/ΔW5`。
- **判定式（不裁定，只给判据式）**：**0x24 臂 ≥1 条连接的"首 4 KB 无重启 ∧ 离线复核 `K0≠0 ∧ breaks==0`"** ⇒ "命中已现形"；**0 条 ∧ 前件达标** ⇒ "本构型下未命中"（⛔ 不许写"不存在"）；**前件不达标** ⇒ "无判别力"（#92）。

**为什么这套读数干净**：命中签与"事件从未发生"在**单连接字节流内**不可区分（设计件 §1.4(P-3) 自证），但**与"C1 的偷槽事件发生过"**（板侧 `ΔW72`/`ΔW71` 记账）合起来就是"发生过 + 流没断" ⇒ 与 pending/clean 形态（**有重启**）逐字节可分。

## §3 Q2：期望门 `Δ(W72+W74) × P` 是否该改 —— 净建议：**改（三条 + 一条备用）**

### ① `ΔW74` 必须删 —— 它结构性进不了装载拍（设计件自证 + 本轮复核）

- 设计件 §1.4(P-1) 已证：**pending 的消费拍在结构上永远 `asm_go=0`**（帧首 `seg_sent==0` 的第一拍恒 `op_pend=1`；`frm_wait` 拍含 `!frm_wait`）⇒ 由 `up_pend_r`（异槽路径）触发的复位**必然干净**。
- 本轮现读复核：`up_pend_r` 分支（`:884-885`/`:891-894`）的消费只经 `up_ev`，其 `up_ok` 在 `!idle_now` 且 `!same_slot` 时恒 0（`:547-549`）⇒ **`ΔW74` 类事件的命中概率恒 0**。
- 影响量级：**P3A0 里 ΔW74 = 0（无影响）；B4H3 里 1/12（+8 %）；C1 构型里 ≈ 2/3（+200 %）**。⇒ 该修正对"高事件密度构型"是**实质**的。

### ② 分子换实测帧率：`P ⟵ ΔW52/ΔW5`（现值 `W51_Bps/(1460×156.25e6)`）

- 装载拍频率 = **帧启动频率**（每帧恰 1 拍）⇒ `P = ΔW52/ΔW5` **就是该频率**，无需经"载荷字节率 ÷ 1460"再换算（等值仅在"帧长恒 1460"时成立；BIZ 轮已有过"1464/1510 vs 1472/1518"的口径事故）。
- 且该形式**自动吸收** app 速率分布：`E = N_同槽 × ΔW52/ΔW5`。P3A0 复算：455,283.94/156,238,379 = 2.914e-3（与原式同值）；长流 S3 锚：156.25e6/200.4 = 779,700 fps ⇒ 4.99e-3。

### ③ 加"构型侧前件"：**"事件到达时 app 在组装"必须结构性论证或直测**——这条是 cfg A 翻车的真原因

- **均匀相位假设在什么构型下显著偏离？** 答：**当事件时刻与 app 的会话生命周期因果耦合时**。cfg A 里，事件（ADD）由"旧连接的死"产生 ⇒ 恒定落在 **[ev_down, app idle]** 窗口（= `closing`）⇒ **不偏离"均匀"，而是整个条件集合是闭合的错误**（P_true = 0 对 P_model = 2.9e-3，**高估**）。另一类耦合：**自时钟构型**（sink 按"收满 N 字节"再断 ⇒ N 字节 = 整数帧 + 固定偏移 ⇒ 相位**锁相**）⇒ 可能系统性**高估或低估**；而 C1 的偷槽时刻 = **板侧 RTO（80 ms，独立于帧循环且非整数帧**：80 ms = 12.5 M 拍 = 64,102.56 帧 @195 拍 ⇒ 非共振）⇒ 均匀假设**在该构型下成立**。
- **操作化**：门里加一行**前件声明**："本臂的 `ΔW72` 类事件到达态 = 组装中（依据 = §2.0 的结构论证 / 或直测）"；**没有这一行，`Δ(W72+W74) × P ≥ 3` 不是功效证书而是空话**（P3A0 就是活例：门说 0.070，语义说 0）。

### ④ 复核一条既有口径（读侧不裁定）：`ΔW73` 的构成

现读 RTL（`:587-591`）：`stat_sw_apply` 计**一切 `sw_apply` 拍**（含登记后的补应用）。⇒ 三态恒等式里的第一项是 `Δ(ev_up ∧ sw_apply)`（**当拍应用**），而 `ΔW73 ≥ 当拍应用`。B4 报告用 `ΔW71 == ΔW73+ΔW74` 做过核对（恰好当臂无补应用时等值）——**今后凡引 `ΔW73` 必须注明"含补应用"**（P3A0：ΔW73 = 36,809 = 36,785 当拍 + 24 补；B4H3：11 = 1 + 10）。

### ⑤ 备用刀（不推荐先做）：直测 H1 分母的计数器（设计件 §1.4 的可选 `stat_p3_win_ev`）

- **它是什么**：`Σ(ev_up ∧ same_slot ∧ active ∧ !closing ∧ !frm_wait ∧ !op_pend ∧ !pw_valid ∧ seg_sent==0)` = **"命中"的直读**（在 `SWC_OK=1` 上纯观测、安全——I1 已保证覆盖不可能，计数器量的是 **would-be 命中率**）。
- **代价**：一次构建（+1×32 位计数器 + 比较锥；快照 **75 → 76 字** ⇒ 未实现地址/读侧链式同步 ≈ 5 文件 + 台账几何）≈ 半天–1 天；DP 域时序风险 = 中等（0x28 的 E12 四计数器锥"不进任何报告面"【已核】，同款做法可期）。
- **收益边界（必须写清）**：**它只在 0x28 上存在** ⇒ 量到的是"修复代上的 would-be 率"，**不能替代 0x24 的 A/B 见证**（0x24 无此仪器）；且 0x28 的行为与 0x24 在被测点上不同（同槽事件在 0x28 走收尾/重应用）⇒ 会有同向而略偏低的系统偏差（量级级可用，逐值不可比）。
- **净建议**：**保留 / 不先做**。先做 §2 的 C1（零构建、且读出的是 0x24 的证据）；只有当 C1 的第 r1 风险成立（`ΔW72 ≈ 0`，即静默释放不成立）而 TL 仍要 P-3 的可达性数字时，才轮到这把刀。
