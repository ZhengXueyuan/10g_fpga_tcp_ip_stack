**最重要的 3 条（按影响排序）**

1. **高-3 + 高-4：端口身份在 TX 侧没有物理通路，且 A-1 的源 IP/校验和改动被漏掉。**
   两级 `tx_arb`（`rtl/tx_arb.v:9-25`，73 位硬编码）之后才做 `tx_split2`；plan 与 P1 都没有给出"port 位如何穿过 `tcp_tx_frame → tx_arb → tx_arb`"的承载方式。更关键：`tcp_tx_frame` 的**源 IP 是常量**（`board/wrapper_p4.v:2331` `.cfg_src_ip(32'hC0A86402)`；`rtl/tcp_tx_frame.v:129,400-401,817-818,874-875,1440,2481` 等），A-1 若要按 `rd_dip` 选口，就必须把**帧头源 IP + IP 校验和 + TCP 校验和种子**全部改成 per-connection；P1 的改动清单只写了"增加 `cam_rd_dip` 输入 + `o_port` 输出"，没有覆盖这三组（且 `tcp_tx_frame` 有 `TCP_TX_OVL` 双体，两体都要改）。这不是"最小改动"。

2. **高-1 + 高-2：S2"单栈双口"的容量/公平性没有写清，P3 的"每口向天花板逼近"判据在结构上不可满足。**
   单栈 + 单条 10G TX + 单条 RX 合并 + 共享 `WIN_POOL=49152 B` 的聚合上限约 9.5 Gbps，不可能"两口各自满 10G"。合并器若照抄 `tx_arb` 的**严格优先**（`rtl/tx_arb.v:42-52`：`s_fast_tvalid` 优先），在持续流量下低优先口会被**整口饿死**；且合并前的 `fifo_async(76×256)` 只能装 **1.36 个最大帧**（1518B = 190 字），没有余量吸收"另一个口连续两帧"的等待。plan §5-P3 判据 #5+#6（双口同时跑 + 每口逼近天花板）需要改写为"聚合 ≤ 天花板 / 每口公平份额 / 丢帧可读"。共享 `WIN_POOL` 下两条连接各分约 24 KB，BDP 在 RTT > 约 19.7 µs 时不够（单条 10G 的已知墙是约 39 µs；项目实测 `srtt 16-27 µs`），两口并存会把窗口墙提前一倍。

3. **高-5 + 高-6：P1 的快照汇合超时是本设计最必要的机制，但 busy/清位语义未钉死；同时 DP 域 FF 预算被低估约一倍。**
   `snap_cdc` 在 `clk_b` 停钟后 `busy_a` 会**永久挂高**（`rtl/snap_cdc.v:78,117` 的 toggle 握手；头注释 `:43-45` 明说"跑一阵再停 ⇒ busy_a 挂高"）。若 `snap_busy` 把 `ch0_busy` 也 OR 进去，第一次超时后主机看到的 busy 永不落；P1 §3.3-6 只写"snap_busy = snap_pending | 四束 busy"，没有明确排除 ch0_busy。另外 P1 §2.5/§3.4 把 DP 域增量写成"~110 FF"，但 ch0 的 PCS 3FF（17×3+8×3=75）、W77 事件计数器（32）、LOS 3FF+计数（约 22）全部在 `dp_clk` 域，DP 域真实增量约 **223 FF**；pcie 域分解写 320 FF，实际 `dout_a`+阵列 = **448 FF**（7×32×2）。0x2A 的全局 WNS 宿主正是 DP setup（`+0.039` = 0.61%），这条低估直接关系"一次构建收口"的成败。

## 2. 分级发现（逐条：文件:行号 · 依据 · 建议）

### 阻断（0）

本轮未发现使 P1 设计在物理/结构上不可实现的阻断项。以下高优先项若不修，会直接变成"实现出来但判据/语义不对"或"构建一次不收口"，故列为高。

### 高（7）

**高-1 S2/P3 的"双口各自满速"判据与单栈/单线/共享窗池结构性矛盾**
- 文件:行号：plan §1.4（甲 = "两条 10G 各跑业务"）、§5-P3 判据 #5/#6（"双口同时跑" + "每口向线上载荷天花板逼近"）；用户裁定 §0.5-5/10（不做 S1、不做独立池）；`WIN_POOL = 49152 B`（仓根 `CLAUDE.md` P7b 硬约束）。
- 依据：S2 = 一套快路径 + **一条** 10G TX 线（`wrapper_p4.v:2891` `u_txcdc(73)` + `:2917` 唯一 `mac_tx_10g`）+ **一条** RX 合并输出（plan §3.2）。聚合上限约 9.5 Gbps；两口同时满速在物理上不可能。共享 `WIN_POOL` 下两条连接各分约 24 KB，BDP 在 RTT > 约 19.7 µs 时不够。
- 建议：把 P3 判据改为"聚合 ≤ 线上载荷天花板 + 每口公平份额 + 每口丢帧/背压计数可读"；在 §2-S2 明确写出"S2 不是 2×10G，而是 10G 聚合分担"；把 `WIN_POOL` 的双连接后果列为已知限制。

**高-2 RX 合并器照抄 `tx_arb` 严格优先 ⇒ 低优先口可被整口饿死；FIFO 深度余量不足**
- 文件:行号：plan §2-S2 #1 / §3.2（"`rx_merge2` = `tx_arb` 同款 FSM，空闲时选一路、锁到 TLAST"）；`rtl/tx_arb.v:42-52`（`s_fast_tvalid` 优先）。
- 依据：`tx_arb` 的帧间重仲裁只有 1 拍；若高优先口在每帧结束后立即有下一帧（10G 线速背靠背），低优先口永远拿不到 `busy`。按 10G 线速，一个 1518B 帧 = 190 字；等待口在这 190 拍里会再收到约 190 字，而 `fifo_async(76×256)` 只有 256 字 = 1.36 帧，剩 66 字余量；一旦排队两帧即溢出。
- 建议：合并器用 round-robin / 轮转（或 deficit round-robin），并保证"每口最多等一帧"；同时把 FIFO 深度/背压策略写进设计（建议 ≥ 2 帧或加 per-port drop 计数）。验收判据要加"两口各灌满时两口都前进"（负对照：改回严格优先 ⇒ 低优先口计数停滞）。

**高-3 TX 端口位没有穿过 `tx_arb` 的物理通路（plan 与 P1 都缺）**
- 文件:行号：plan §3.2 TX 侧（split 在 `u_txcdc` 之前）+ §3.2 "字宽连锁：TX 字 73→74"；P1 §2.2（"port 位在 split 处被消费，不进 FIFO"）；`rtl/tx_arb.v:9-25`（73 位硬编码）；`board/wrapper_p4.v:2814`（`u_tx_udp_arb`）/`:2865`（`u_tx_arb`）/`:2891`（`u_txcdc`）。
- 依据：TX 数据在 `tcp_tx_frame`/`udp_tx_frame`/`slow_tx_adp` → 两级 tx_arb → `u_txcdc`。若 port 位不进 FIFO、又在 split 处被消费，它必须在两级 tx_arb 之前就进入数据流（74 位），穿过两级 arb 后由 split 剥离；plan 的"字宽连锁"没有列 `tx_arb` 的加宽，P1 的"73 位、两条"也只说 FIFO。

## 5. 待裁问题复核（含遗漏项）

### 5.1 P1 §6.4 的 14 行（不是派单说的 9 条）

P1 §6.4 实际列出 **14 条**待裁：1 基代、2 BID、3 观测档位、4 快照超时、5 乙转发目的地、6 甲 HLS 两 IP、7 甲出口身份、8 `p7b_chain` 入矩阵、9 LOS 负对照方式、10 乙位流暂缓、11 ch0 TX MAC、12 stub 拆 status、13 `0x08` bit1 纪律、14 排期。派单描述"9 条"与文档不符；进度件摘要列 10 条（把 1 基代已裁、若干合并）。建议 P1 下一版把"已裁/待裁"分栏。

### 5.2 哪些不应由用户裁（技术细节，建议设计所有者直接定）

- #4 快照超时机制：这是 P1 的必需防御，不是偏好问题；用户只需知道"会新增一个 `SNAP_STATUS[7]` 语义"。
- #8 `p7b_chain` 入矩阵：是工程质量门，应由门所有者/构建所有者定。
- #12 stub 拆 ch0/ch1 status：纯仿真面，门所有者定。
- #13 `0x08` bit1 固定 0：施工纪律。
- #14 排期/并发：TL 排期。
- #2 BID 0x2B/0x2C：通常由构建纪律（bump）决定；用户只需确认可用。

### 5.3 应由用户裁/确认的（保留）

- #1 P1 基代 = 0x2A：已由用户 18:38 裁定；P1 位流会带上孤儿修复（0x2A 内容），与用户已批准 0x2A 现役一致。
- #3 观测档位：+7 字会吃 WNS；用户可裁"最小集（W76+W78+W79/W80）"。
- #5 乙模式转发目的地：B-1（PCIe C2H）vs B-2（ch1 线上）vs B-3（只计数）；产品语义，必须用户裁。
- #6 HLS 两 IP 改动授权：甲模式的硬前置；用户裁定 #2b 已隐含授权，但 P1 应显式请用户确认"允许改 HLS + 重综合"。
- #7 甲出口身份：A-1（无标签）与 §0.5"其余按推荐（CAM+1）"冲突，必须重新裁定（见高-4）。
- #9 LOS 负对照方式：物理拔 AOC vs 对端 `ip link down`；涉及现场操作。
- #10 乙位流暂缓：用户说"两个 bitfile"，P1 建议 P1 只建甲；需用户确认"先甲后乙"是否可接受。
- #11 ch0 TX MAC：P1 建议不加（P0 已证 IDLE 足够）；可由设计定。

### 5.4 遗漏的待裁/待确认项（本审查新增）

1. A-1 与 §0.5 的路线冲突（高-4）：应列为用户重新裁定项，而不是"设计细化"。
2. S2 聚合上限与"双口各自满速"的目标冲突（高-1）：需要用户确认"甲 = 聚合 10G 分担"而不是"2×10G 同时满速"。
3. 共享 `WIN_POOL` 的双连接 BDP 后果（高-1）：需要用户知道"不做独立池"的真实代价。
4. `cfg_src_mac` 是否 per-port：同一 MAC 双口在直连构型可行；若未来接交换机/同一 L2，需要两个 MAC。P1/plan 都没提。
5. 乙模式镜像是否含 FCS/元数据：raw-frame tap 是 MAC 之后（FCS 已剥离），主机拿到的是"无 FCS 的帧 + `tcrs/terr` 边带"；用户说"转发 RX"是否接受这个口径，未裁。
6. 镜像/转发的背压策略：乙模式主机读得慢时是"丢整帧"还是"停 ch0 RX"（停 RX 会反压 PCS ⇒ 可能丢对端帧）。plan/P1 只说"满则丢整帧"，需要用户定"允许丢"的语义。
7. 甲模式第二 IP 的对端配置（p0 的 IP/路由）与 HLS 两 IP 的地址值：产品配置，需用户定。
