## 0. 一页结论（先读这个）

| # | 结论 | 等级 |
|---|---|---|
| 1 | ⛔ **S2 单栈在结构上到不了 2×10G**：只有**一条** 10G TX 线（`wrapper_p4.v:2891` `u_txcdc` → `:2917` 唯一 `u_mac_tx`）、**一个** RX 入口（`:854` `u_mac_rx` 只接 ch1；ch0 RX 无消费者）、**一套** app/窗口池（`rtl/app_ctrl.v:276` `WIN_POOL=16'hC000`=49,152 B）。2×9.5 Gbps **不是"优化"能补上的 2× 差距，是缺一套独立数据面** | 【已证·源码】 |
| 2 | ⭐ **物理层不是瓶颈**：现役 `pcs64` 就是 **2 通道核**（`NUM_OF_CORES=2` / X0Y4=X0Y5 两子核各 10.3125 Gbps）；闸 1 已证两通道同时工作（30,056,095 帧零错）；P0 已把 J7 模块 + 第二根 AOC + 对端 p0 link 10G 抬到板级已证。**"接入第二口"零 GT/PCS 改动** | 【已证·构建/板级】 |
| 3 | ⭐ **最低资源成本方案 = B/C2**：**双快路径（各一套 MAC/TCB/重传/窗口）+ 单份双 IP HLS 慢路径 + 每口 retx 8 连接×64 KB 分区**。增量约 **+32–34k LUT / +19–20k FF / +19 BRAM / +0 URAM / +0 DSP**（纸面）；总量约 **111k LUT（51%）/ 95k FF（22%）/ 367 BRAM（76.5%）/ 1 URAM** | 【纸面】（锚 = P6a 分层实测 + MAC OOC，见 §2） |
| 4 | ⚠️ **BRAM 是真正的分水岭，且结论与 plan 不同**：plan 说"S1-full 不可行"——**只在每口 16 连接×64 KB 时成立**（+256 tile ⇒ 623~660 > 480）。**每口 8 连接×64 KB 时，两套 retx 合计仍是 256 tile ⇒ BRAM 与今天相同**；**A（完全双栈，含双 HLS，每口 8×64 KB）也只有 404/480 = 84.2%**，**无需 URAM 迁移** | 【纸面/已证·源码】 |
| 5 | ⚠️ **每连接 ring 深度被 `WIN_CAP_5=0xF000`（61,440 B）钉死**：结构性界 = `(61440−1)+1500 = 62,939 < 65,536`。若把 ring 减到 32 KB，必须同时把 `WIN_CAP` 降到 ≲31 KB（10G BDP 的 RTT 上限从 ~39 µs 掉到 ~24.8 µs，而实测 srtt 16–27 µs ⇒ 贴边）⇒ **推荐 8×64 KB，不推荐 16×32 KB** | 【已证·源码】+【纸面】 |
| 6 | ⚠️ **URAM 迁移路线比派单描述的更紧**：`retx_ram` 单套 29–32 URAM；**板上已有 1 个 URAM（M1 镜像）** ⇒ 两套 = **59–65 / 64**。**29/套 才刚好放下（59/64）；32/套 = 65/64 放不下**。且 KU5P 的 64 个 URAM **全在 X2 一列**、X2Y1 的 BRAM 已满 ⇒ 布局风险高 | 【已证·构建/源码】`P7B_BRAM_REPORT.md:24,112-124` |
| 7 | ⭐ **共享慢路径是本方案最大的语义风险，不是面积风险**：单份 HLS 要同时认**两个板 IP**（`hls/src/eth_types.h:119-123` 是编译期常量，`layer_arp.cpp:149,194`、`layer_tcp.cpp:177,277,292`、`layer_udp.cpp:168` 等 7 处用它），且 cfg/TX 要按本地 IP 分流到两套 CAM/TCB。`MAX_TCP_CONN=3` ⇒ **全系统同时建连上限仍是 3**（两口中各 1 条够用；各 2 条不够） | 【已证·源码】 |
| 8 | ⭐ **快路径的"源 IP"不是障碍**：`tcp_tx_frame` / `udp_tx_frame` 的 `cfg_src_ip`/`cfg_src_mac` **本来就是端口**（`rtl/tcp_tx_frame.v:128-129`、`rtl/udp_tx_frame.v:36-37`）。双快路径里每套实例接自己的常量即可 ⇒ **不需要**在 `tcp_tx_frame` 体内做 per-connection 源 IP/校验和改造（这与 S2 单栈审查高-4 的结论不同，因为 B/C 复制了 `tcp_tx_frame`） | 【已证·源码】 |
| 9 | **推荐**：满足 2×10G 的**最低资源成本 = B/C2**；若把"HLS 改双 IP + 跨口慢路径耦合"判为不可接受，则退 **A′（完全双栈，每口 8×64 KB）**——多花 ~+20k LUT/+18k FF/+37 BRAM，但换端口间完全隔离、HLS 只把本地 IP 做成输入参数（不做双 IP 成员判定） | 【推断】 |
| 10 | ⚠️ **"每口 8 连接"是双栈位流的产品取舍，不是单口回归**：单口默认位流仍保持 16 连接（零改动）；双栈位流里两套 retx 各 8 连接（合计仍是今天的 256 tile）。若坚持"口 A 16 + 口 B 8"，BRAM = 495/480（超 15 tile），需再用 HLS 小 RAMB18→LUTRAM 省 ~25 tile（纸面，`P7B_BRAM_REPORT.md:170-173`）才可行 | 【纸面】 |
| 11 | ⛔ **时序无法给可信预测**：0.61% 余量、当前 DP 关键路径 **68% 是布线**（`logic 1.855 / route 4.371`），加 ~32k LUT 到同一 `dp_clk` 域会改变拥塞/布局。**只能"一次构建收口 + 预登记 backstop"**，不写假精确 WNS | 【已证·构建】+【推断】 |

## 1. S2 单栈为什么结构上到不了 2×10G（源码/资源证据）

### 1.1 TX：只有一条 10G 线

| 事实 | 位置 | 后果 |
|---|---|---|
| 唯一 `mac_tx_10g` 只驱动 `tx_mii_d_1/tx_mii_c_1`（ch1 = J8） | `board/wrapper_p4.v:2917-2939` | 第二个口没有业务 TX |
| ch0 TX = **常量 IDLE**（`dont_touch` 寄存器，`64'h0707…/8'hFF`） | `:601-608` | 只能维持链路，不能发帧 |
| 唯一 `fifo_async(73×256) u_txcdc` | `:2891` | 一条跨界，无法同时载两口的 10G |
| 两级 `tx_arb`（UDP 压 HLS、TCP 严格优先）都是 73 位单流 | `:2814` / `:2865`；`rtl/tx_arb.v:9-25` | 所有 TX 生产者共用一条出口 |

⇒ 即使把 ch0 TX 接上，只要仍然共用 `u_txcdc`/`u_mac_tx`，**总量上限就是一条 10G 线**（~9.5 Gbps 线上载荷）。

### 1.2 RX：只有一个入口 + 一套快路径

| 事实 | 位置 |
|---|---|
| 唯一 `mac_rx_10g u_mac_rx` 只接 `rx_mii_d_1/rx_mii_c_1` | `:854-890` |
| ch0 `rx_mii_d_0/rx_mii_c_0` **无消费者**（只有 PCS 状态 XOR 成 W39[30] 的 1 位签名） | `:452-453`；`:3665-3670` |
| 唯一 `u_rxcdc(76)`、`vlan_strip`、`rx_classify`、`tcp_rx`、`tcp_echo` | `:932`、`:975`、`:998`、`:1909`、`:2012` |
| S2 计划里的 `rx_merge2` 也只能把两口**合流进同一个** `tcp_rx`/`tcp_tx` | plan §3.2；审查高-1/2 |

⇒ S2 的聚合上限仍是 **~9.5 Gbps**；合并器还会引入公平性/饿死问题（审查高-2：`tx_arb` 严格优先 + 合并前 FIFO 256 字 = 1.36 个最大帧）。

### 1.3 单套 app / 窗口池

| 事实 | 位置 |
|---|---|
| 单 `app_ctrl`，`WIN_POOL = 16'hC000 = 49,152 B`（全局信用池） | `rtl/app_ctrl.v:276`；wrapper 例化 `:1339-1348`（未覆盖该参数） |
| 单 `tcp_echo` 的 `frame_fifo`（16 BRAM = 64 KB）是 RX 物理缓冲 | `rtl/tcp_echo.v:93`；`rtl/frame_fifo.v:147`；P6a 分层 16 tile |
| 单 `tcp_tx_frame` / `tcb` / `tcp_cam` / `retx_ram` | `:2276` / `:2093` / `:2069` / `rtl/retx_ram.v` |

⇒ 两条连接共享 49,152 B ⇒ 各 ~24.6 KB ⇒ 10G 的 BDP 墙提前到 **RTT ≈ 19.7 µs**（`24576×8/10e9`）；项目实测 `minrtt 6–8 µs / srtt 16–27 µs`（`P7B_OPEN_ITEMS.md:196`）⇒ **上沿已越墙**。

### 1.4 实测天花板（单口）

- 单连接持续下行：**板侧内窗 9.108 Gbps / 对端墙钟 9.314 Gbps**（`p7b_longflow_board/ACCEPT.md:66-67,144-149`）。
- 设计上界 `1460×8×156.25e6/193 = 9.456 Gbps`；线上载荷天花板 `1460/1538×10 = 9.4935 Gbps`。
- ⇒ 单口已经贴到 ~98%；**2×9.5 需要两条这样的线，而不是把一条线再压 2 倍**。

### 1.5 物理层不是限制（关键反证）

- `pcs64` 是 **2 通道核**：`build_p7b_ku5p.tcl:48-65` 的 `NUM_OF_CORES=2 / LANE1=X0Y4 / LANE2=X0Y5`；两子核 `.xci` 回读各 10.3125 Gbps / QPLL0（`plan DESIGN.md:22`；审查 A4）。
- 闸 1：两通道同时工作，**30,056,095 帧零错 / 9,999.94 Mbps**（`P7B_GATE1.md:25-31`）。
- P0：J7 模块 + 第二根 AOC + 对端 p0 **link up 10G**；`0x08` bit0 负对照有牙且单口隔离（`p9_dual_sfp_p0_20261017/README_FOR_TL.md:12-22`）。
- ⇒ **第二口缺的 100% 是数据面与观测面**，不是 GT/PCS/线缆。

## 3. 选项定义与资源增量

### 3.1 四个选项（本件口径）

| 选项 | 快路径 | 慢路径 HLS | 存储 | 备注 |
|---|---|---|---|---|
| **A** | 两套完整（MAC/RX/TCP/UDP/app/TCB/CAM/retx） | **两份**（各一个 `udp_echo` 实例，本地 IP 作为实例常量/参数） | 每口独立 retx + 每口 tcp_echo | "完全独立" |
| **A′** | 同 A | 两份 | **每口 retx 8 连接×64 KB** | 本件推荐的 A 变体（BRAM 可行） |
| **B** | 两套完整 | **一份，支持双 IP/双口** | 每口独立 retx + 每口 tcp_echo | 共享慢路径 |
| **C** | 同 B | 同 B | **retx 按口分区（C2）/ 窗口池共享（C3）** | C2 = B 的 8×64 KB 分区；C3 评估为不可取 |
| **D** | 现状 S2 | 一份 | 单 retx + 单 tcp_echo | 对照：聚合 ~9.5 Gbps |

### 3.5 BRAM/URAM 账（逐项，重点）

**现状 348 tile 的组成**（`P7B_BRAM_REPORT.md:34-43`）：

```
retx_ram 256  +  HLS udp_echo 37  +  XDMA 36  +  tcp_echo.u_fifo 16  +  3×frame_fifo(1+1+1) = 348
```

**推荐 B/C2（每口 8 连接×64 KB）**：

```
第一套 retx 128（原 256 → 128）
第二套 retx 128                     ← 两套合计 256 = 与今天完全相同的存储总量
第二套 tcp_echo 16
第二套 slow_rx/slow_tx/udp_split frame_fifo 3
共享 HLS 0（不变）
────────────────────────────────────
348 − 256 + 128 + 128 + 16 + 3 = 367 tile（76.5%）
URAM = 1（M1 镜像，不变）
```

⚠️ **这是"双栈位流"内的账**：单口默认位流仍保持原 16 连接 retx（256 tile，零改动）。双栈位流把**两套** retx 都缩到 8 连接（合计仍 256）；即口 A 在双栈位流里也降为 8 连接。若坚持"口 A 16 + 口 B 8"：348 + 128 + 16 + 3 = **495 > 480（超 15 tile）**，需再靠 HLS 小 RAMB18→LUTRAM 省 ~25 tile（纸面）——不推荐作为第一版。

**A′（完全双栈，每口 8×64 KB）**：367 + 第二份 HLS 37 = **404 tile（84.2%）**，URAM 1。

**为什么不能"16 连接×32 KB"**：

- 每连接 ring 的结构性安全界（现役 `WIN_CAP_5 = 0xF000`）= `(61,440−1) + PLEN_MAX 1,500 = 62,939 < 65,536`（`rtl/retx_ram.v:5-11`；`tcb.v:144-147`）。
- ring 若只有 32 KB，则该界 **62,939 > 32,768** ⇒ 直接破坏"最坏在飞不覆盖未重传数据"的安全论证。
- 要保 16×32 KB，必须把 `WIN_CAP` 同时降到 **≤ ~31 KB** ⇒ 10G 的 BDP RTT 上限 = `31,000×8/10e9 = 24.8 µs`；实测 srtt 16–27 µs（上沿超）⇒ **不可取**。
- ⇒ **每连接 64 KB 是现役窗口帽的硬配套；2×10G 的 BRAM 中性方案只能是 8 连接/口。**

**URAM 迁移路线（若坚持 16 连接/口）**：

- `retx_ram` 单套 **29–32 URAM**（`P7B_BRAM_REPORT.md:24,119-124`）；两套 **58–64**；板上已有 1（M1 `mir_uram_fifo`）⇒ **59–65 / 64**。**29/套刚好（59），32/套放不下（65）**。
- 额外代价：读流水 **2→3 级**；`tcp_tx_frame` 的 `S_RING` 拍表（`ring_end = nbeats+2` 的 `+2`）要重算 + 全链回归（`P7B_BRAM_REPORT.md:136-145`）；不能只加 `ram_style="ultra"`（会炸成 8 lane×16 片 ⇒ 128 URAM/阵列，`§3.5`）。
- 设备约束：KU5P 的 64 个 URAM **全在 X2 列**（每区 16）；X2Y1 的 BRAM 已满 72/72（`P7B_BRAM_REPORT.md:112-113`）⇒ 布局/布线风险高。
- 结论：**不是首选**；只在"必须 16 连接/口"且接受一次独立的 URAM 迁移轮时才考虑。

### 3.6 窗口池 / BDP 存储

| 项 | 现状 | 2×10G 需要 | 存储 |
|---|---|---|---|
| RX 物理缓冲 | 单 `tcp_echo` `frame_fifo` **64 KB = 16 BRAM** | **每口一个**（两个 app 各自零拷贝） | **+16 BRAM**（已计入） |
| RX 通告信用 `WIN_POOL` | 单 `app_ctrl` 默认 **49,152 B** | **每口一个 49,152 B**（两个 `app_ctrl` 实例）⇒ 10G BDP 支持 RTT ≤ **39.3 µs** | 0（信用不是存储） |
| 若共享一个 `WIN_POOL`（C3） | 49,152 B 两口分 | 各 24.6 KB ⇒ RTT ≤ **19.7 µs**（实测 srtt 上沿 27 µs） | 0，但 **BDP 不够** |
| 若要抬 RX 窗口到 60 KB/口 | — | 物理界 = `Σwinq + N·ACC_MARGIN + Δ + U + SEG ≤ 65,536` ⇒ 单连接上限 **≈55.6 KB**（`CLAUDE.md` P5d 段；`P7B_HANDOFF.md:309`） | 不增存储；但 `WIN_POOL` 参数需每口单独设 |
| TX 重传环 | 256 tile（16×64 KB） | **每口 8×64 KB = 128 tile** | 两套合计 **= 256 tile（净增 0）** |

⇒ **推荐"每口一套 `app_ctrl`/`tcp_echo`"**；窗口池不做跨口共享（C3 只省 0 tile，却把 BDP 墙砍半）。

⚠️ **术语澄清**：任务里"两连接各 ~60 KB 的 BDP"在本设计里由**两处存储**承载 —— TX 侧 = `retx_ram` **64 KB/连接**（8 连接/口 ⇒ 512 KB/口）；RX 侧 = `tcp_echo` 的 `frame_fifo` **64 KB/实例**（每口一个 = 16 BRAM）。`WIN_POOL`（49,152 B）是**通告信用**，不是数据存储；它只决定"允许对端在飞多少"，其上限受 `frame_fifo` 容量与 P5d 物理界约束（单连接 ≤ ~55.6 KB）。

## 4. 时序风险（不给假精确 WNS）

### 4.1 基线

| 项 | 值 | 出处 |
|---|---|---|
| 全局 WNS / WHS | **+0.039 / +0.010 ns**（周期 6.400 ⇒ 余量 **0.61%**） | `p9_build_0x2A/README_FOR_TL.md:39` |
| 全局 WNS 宿主 | **DP setup**：`u_tcp_tx/u_fifo_b/rptr_reg[3]/C → u_app/stg_reg[26]/D`（19 级，**logic 1.855 / route 4.371** = 68% 布线） | 同上 `:50-51` |
| 三类失败端点 | 0 / 0 / 0 | 同上 |
| DP 域 | 单域 `dp_clk` 156.25 MHz；两口共用一个时钟域 | `wrapper_p4.v` DP 结构 |

### 4.2 加双套的预期影响（定性，不给数值）

1. **同一 `dp_clk` 域里再放一套 ~32k LUT 的数据面**：最差路径的**同一对源/宿会出现两份**；当前这条路径 68% 是布线 ⇒ 对拥塞/布局敏感。**0.61% 余量下，"能不能收口"无法从纸面判断**。
2. **新增跨域点**：第二套 `rxcdc`/`txcdc`（ch0 的 `rx_clk_out_0`/`tx_mii_clk_0` 已是现役时钟，负载 1428/577；只是加消费者）。XDC 时钟组预计已覆盖（`gtrefclk0` 系 `-include_generated_clocks`），但**必须**在构建轮用 `report_clock_interaction` + `12-4739` 复核。
3. **快照/PCIe 域**：每口独立计数至少 +6–8 字（每字 ≈ +96 FF，三份）⇒ +0.6–0.8k FF；其中 DP 侧 ~+100–200 FF。**0x28 的全局 WNS 宿主曾是"快照阵列异步复位族"**，加字可能把宿主换回去 ⇒ 观测扩容是**第二号时序风险**。
4. **A′ 比 B/C2 多 ~20k LUT**：面积仍够（60% vs 51%），但 dp 域拥塞更高 ⇒ **时序风险更大**；换来的是没有跨口 merge/demux。

### 4.3 backstop（构建前预登记，按顺序）

| 顺序 | backstop | 省/效果 | 备注 |
|---|---|---|---|
| 1 | 双栈构建里**裁掉可选调试件**（`u_dbg_line` 3,410 LUT / `u_app_status` 1,121 LUT） | 省 ~4.5k LUT | 只省面积，不保证救 WNS |
| 2 | **最小观测集**（第二口只留 4 字：好帧/字节/FCS 错/丢帧） | 少 +2–4 字 | 保留主判据 |
| 3 | 每口 retx **8 → 4 连接**（64 tile/栈） | BRAM 降到 ~239 | 产品并发再降；单流目标不受影响 |
| 4 | 跨口 slow merge/demux 加寄存器切片（1–2 拍） | 切断新组合长链 | 增加慢路径延迟（可接受） |
| 5 | 若仍负：**不重跑到过**（纪律）⇒ 回退上一代位流，另开设计轮 | — | "一次构建收口" |

⚠️ **不许**把"把两口拆成两个 bitfile 各跑单口"当 2×10G 的替代 —— 那不满足"同时"。

## 6. 对端/台架能力

### 6.1 对端事实

- SFC9120 **双口**：`01:00.0/01:00.1` → `enp1s0f0np0`（p0，MAC …:00）/ `enp1s0f1np1`（p1，MAC …:01）；两个独立 PCI function（`P7B_U7_AND_PEER.md:246-278`）。
- P0 实测：板 J7 ↔ p0，**p0 link up 10000Mb/s**；`0x08` bit0 负对照有牙且不影响 p1（`p9_dual_sfp_p0_20261017/README_FOR_TL.md:12-22`）。
- 单口吞吐实测（p1）：**9.108 Gbps（板内窗）/ 9.314 Gbps（对端墙钟）**，lane8 逐字节全查（`p7b_longflow_board/ACCEPT.md:66-67,144-149`）。
- 单口台架的接收侧 = 双线程 sink（I/O + 校验）+ 绑核 + `lane8`；关掉网卡 RX 中断合并是达标前提（`Adaptive RX: on, rx-usecs 60` → 关；`ACCEPT.md:113-122`）。

### 6.2 2×10G 同时收：**未测**

- 双口同时 2×9.5 Gbps ≈ **2.375 GB/s** 到主机；SFC9120 在 CPU 直连槽 **Gen3 x8**（~7.9 GB/s）⇒ **PCIe 带宽名义足够**。
- 但用户态接收需要 **2 个 sink 进程 × 2 线程 = 4 核**（I/O+校验各一）+ 两口 IRQ 亲和 + 两口都关 coalescing；对端 CPU 核数/IRQ 拓扑本轮**未登记、未测**。
- 因此：**"台架能不能同时收 2×9.5"=【未测】**；不能拿单口 9.3 的读数外推。

### 6.3 若台架达不到，判据怎么设计

| 判据 | 仪器 | 独立性 |
|---|---|---|
| 每口线上载荷 | **板侧该口 MAC 的字节/帧计数**（两套 MAC = 两个独立实例） | 板内，但与发送同源 |
| 每口接收 | 对端 **该口 NIC 硬件计数** `ethtool -S <if> \| port_rx_bytes/packets` | **对端独立硬件**（Stage 2 `J0` 同款用法） |
| 同时性 | 同一时间窗内**两口计数都单调推进**；每口各自与 NIC 计数对账（±0.2% 量级） | 两条独立链 |
| 单口隔离负对照 | 写 `0x08` bit0/bit1 分别拉高 `sfp1_tx_dis`/`sfp2_tx_dis` ⇒ 只有该口停、另一口继续 | P0 已证 bit0；bit1 需复算 |
| 内容 | 两口各自 `mism_bytes=0`（逐字节）——若 CPU 不够，降速或**逐口顺序**做内容，另用硬件计数证明"同时满速" | 口径必须写清 |

⚠️ **不要**把 PCIe 镜像（M1 C2H，~1.7 GB/s）当 2×10G 的唯一 oracle：2×1.19 GB/s = 2.38 GB/s **超过**该通道能力；它只能做诊断，不能做同时满速的唯一证据。
⚠️ 快照在高速下会变慢（12 字 ~288 ms > 整条流 227 ms，`ACCEPT.md:132`）⇒ 双口读数用**短表**或独立计数窗口。

## 7. 兼容性（单口零回归 / 双 bitfile / BID）

### 7.1 构建开关

- 新宏 **`DUAL_STACK`（默认关）**：默认构建 = 现役 S2 单口，**逻辑等价/零回归契约**（所有新逻辑包在 `` `ifdef DUAL_STACK `` 内；关闭时新端口接常量）。⚠️ 对 wrapper 的结构性编辑**不承诺逐位网表相同**（行号/命名/代码移动可改变网表）；验证 = 默认构建的资源/门零回归 + 与现役 0x2A 的同档 A/B。参数级"默认关 = 逐位退化"的 `fc /b` 先例（`app_pattern`）只适用于参数级改动。
- **甲 = `DUAL_STACK=1`**（双口业务，2×10G）；**乙 = `SFP2_MODE_B=1`**（只转发 ch0 RX 镜像，不建连）。
- **硬门**：`DUAL_STACK ∧ SFP2_MODE_B` 同时定义 ⇒ 例化不存在的模块， elaboration 硬失败（照 `g_orph_zw_guard` 手法，`wrapper_p4.v:226-241`）。
- 单口模式在双栈位流里的回归：同一套 per-stack 逻辑不变，但布局会变 ⇒ 需要**同会话 A/B**（双栈位流只跑一口 vs 现役 0x2A）证明业务读数/mism 同档。

### 7.2 两个 bitfile 与 BID

| 位流 | 宏 | 内容 | BID |
|---|---|---|---|
| 单口（默认/参考） | 无 | 现役 S2 | 当前 0x2A |
| 甲（2×10G） | `DUAL_STACK=1` | 双快路径 + 双 IP 慢路径 | **下一空闲值**（0x2B 起；每次构建 bump） |
| 乙（ch0 RX 镜像） | `SFP2_MODE_B=1` | ch0 MAC + RX tap + 镜像出口，无第二套 TCP | 另一 BID（与甲不同几何，读侧要各自一阶段） |

- 全代位流同尺寸（15,431,261 B）⇒ **只有 sha256 + BID 能分版**；每个 bitfile 都要归档 sha256 + 构建输入哈希。
- 读侧 `apply_readside_bid1c.py` 每代新增阶段；未实现地址随 `SNAP_NW` 变（现 0x160）。

### 7.3 观测面

- 第二口需要独立计数束（ch0 的 `rx_clk_out_0` 域 + `tx_mii_clk_0` 域）⇒ 新增 `snap_cdc` 束 + `SNAP_NW` 增加；**必须**同时实现"快照汇合超时"（ch0 停钟时整窗不可读；审查高-5；`SNAP_STATUS[7]` 语义），且 `snap_busy` **不得** OR 进 `ch0_busy`（否则主机轮询挂死）。
- 推荐最小集：ch0 PCS 状态 1 字 + LOS 1 字 + ch0 MAC 好帧/字节/FCS 错/丢帧 4 字 = **6 字**（+576 FF，纸面）；不够再加。

### 7.4 HLS 单/双口兼容

⚠️ **"甲"的口径在本轮发生位移**：plan 的 P1/P2「甲」= **S2 单栈双口**（聚合 ~9.5 Gbps）；本件的「甲」= **双栈 2×10G**（两口各自 ~9.5 Gbps）。两者不是同一个位流；若用户只保留旧的 S2 甲，它仍然到不了 2×10G。乙（ch0 RX 镜像）不受影响。

- 单口模式：保留现 `BOARD_IP`（192.168.100.2）行为；双口模式：`{IP0=192.168.100.2, IP1=192.168.100.4}`（示例）成员判定。
- 改动点（现读）：`hls/src/eth_types.h:119-123`；`layer_arp.cpp:149,194`；`layer_ip.cpp:76`；`layer_icmp.cpp:142`；`layer_igmp.cpp:121`；`layer_udp.cpp:168`；`layer_tcp.cpp:177,277,292`；`udp_echo.cpp` 顶层。
- `MAX_TCP_CONN=3`（`layer_tcp.cpp:10-11`）⇒ **全系统同时连接上限 3**；两口中各 1 条 = 2（够）；各 2 条 = 4（不够）。若要更多，需同时扩 HLS 连接表（每连接 ~1–2 RAMB18 + FF，纸面）。
- **MAC 地址**：现役 `BOARD_MAC = 00:0A:35:01:FE:C0` 也是编译期常量（`hls/src/eth_types.h:112-117`）。快路径每个 `tcp_tx_frame` 实例可以各接一个 MAC 常量；但 HLS 的 ARP 回复用同一常量。**建议每口一个 MAC**（直连双口时同 MAC 也能工作，但同一 L2/交换机下有歧义）；若做双 MAC，HLS 也要按本地 IP 选源 MAC（同一次改动面）。
- 两份 HLS（A′）则各 3 条，共 6；但面积 +19.8k LUT / 37 BRAM / 4 DSP。

### 7.5 app 寄存器总线

- 现 `app_reg_addr/wr/wdata` 在板级**静态钉死为 0**（`wrapper_p4.v:1319-1322` 一带，历史注释"将来接 AXI-Lite 桥"）⇒ 双 `app_ctrl` 目前都不被 host 访问，**无额外成本**。
- 将来接 host app 时，需要**每口一个地址域/端口位**（或两个 AXI-Lite 从口）——登记为后续项。

## 8. 推荐

### 8.1 主推荐：**B/C2**（资源最低，满足 2×9.5 Gbps）

**= 双快路径（两套完整 MAC/TCP/UDP/app）+ 单份双 IP HLS 慢路径 + 每口 8 连接×64 KB retx 分区 + 每口 tcp_echo/app_ctrl。**

理由：
1. **它直接消除 S2 的两条结构性瓶颈**：两条独立 TX 线（各 `txcdc` + `mac_tx`）、两条独立 RX 入口（各 `rxcdc` + 快路径），不再有单线/单流/单窗池。
2. **BRAM 中性**：两套 retx 合计 = 今天的 256 tile；总 367/480，**不需要 URAM 迁移**（避开 59–65/64 和 X2 列布局风险）。
3. **面积宽裕**：110–112k LUT（51%）、94–95k FF（22%）。
4. **慢路径只做一次双 IP 改动**：比 A′ 少 20k LUT / 37 BRAM / 4 DSP。
5. **快路径源 IP 零内部改造**：每个 `tcp_tx_frame`/`udp_tx_frame` 实例接自己的 `cfg_src_ip/mac`（现成端口）。

⛔ **对 §0.5「不用独立连接池」的重新裁定点（必须显式确认）**：本推荐实际上是**每口 8 连接的按口分区**（两套 retx 各 128 tile）。备选的"共享 16 槽动态池 + 单个 retx"在 2×10G 下**不可行**：两口 TX 每拍都要写，单个存储器只有一组写口；加第二写口要把 bank 数翻倍 ⇒ **512 tile**（>480）。因此"2×10G"与"完全共享的重传池"在现役器件上不能同时成立。用户需要在**每口 8 连接（推荐）**与**16 连接/口 + URAM 迁移（59–65/64）**之间重新裁定。

### 8.2 风险对冲：**A′（完全双栈，8×64 KB）**

若"HLS 双 IP + 跨口 merge/demux"被判为不可接受（这是本方案唯一的语义级改动），A′ 是**风险更低**的替代：
- 每口一个 HLS（本地 IP 作为实例常量/参数），**HLS 内部不做双 IP 逻辑**；
- 无跨口 slow merge/demux；
- 端口间完全隔离（一口的慢路径 bug 不影响另一口）；
- 代价：**+20k LUT / +18k FF / +37 BRAM / +4 DSP**，总量仍只 60% LUT、84% BRAM，**可行**。

### 8.3 代价表（推荐 B/C2）

| 项 | 增量 | 总量 | 备注 |
|---|---|---|---|
| LUT | **+32–34k** | ~110–112k（51%） | 纸面；锚 + 增量 |
| FF | **+19–20k** | ~94–95k（22%） | 纸面 |
| BRAM | **+19** | **367/480（76.5%）** | 两套 retx 合计仍 256 |
| URAM | **+0** | 1/64 | 避开迁移 |
| DSP | **+0** | 4/1,824 | HLS 共享 |
| GT | 0 | 6/16 | 两通道已在核里 |
| 时序 | 未知 | 0.61% 基线 | 一次构建收口 + backstop |
| 轮次 | **9–11 轮** | — | §5.2 |
| 台架 | 2 口同时收 **未测** | — | 需 4 核 + 两口 coalescing 关 |

### 8.4 最关键 3 个风险（按影响排序）

1. **时序收口（0.61% + 68% 布线的 DP 关键路径 + ~32k LUT 同域）**：纸面无法预测；只能一次构建收口，backstop 依次裁调试/观测/连接数/加流水；拆两个 bitfile 不满足"同时"。
2. **BRAM/连接数的产品取舍**：2×10G 需要 **每口 8 连接×64 KB**（BRAM 中性）或 **URAM 迁移 59–65/64**（贴满 + X2 列 + 读流水 2→3 + `S_RING` 拍表重算）。16 连接/口 + 纯 BRAM 结构性不可行（623/660 > 480）。
3. **共享慢路径的 HLS 双 IP 改动（语义风险）**：单份 HLS 必须认两个板 IP、按本地 IP 回包并分流 cfg/TX；改错会破坏单口零回归；`MAX_TCP_CONN=3` 同时是总连接上限。若不愿承担，退 A′。

> 第 4 个（不在前 3 但必须登记）：**对端 2×9.5 同时接收未测**；台架若不够，判据必须用"每口 NIC 硬件计数 + 每口板侧计数"两条独立链，而不是 PCIe 镜像或单口外推。

### 8.5 不推荐 / 不可行

| 项 | 原因 |
|---|---|
| **D（S2 单栈）** | 结构上聚合 ~9.5 Gbps，2×10G 不可达；只作对照 |
| **A（16 连接/栈，纯 BRAM）** | 660 > 480，不可行 |
| **A/B（16 连接/栈，URAM）** | 59–65/64；32/套放不下；X2 单列 + X2Y1 BRAM 满；读流水/S_RING 返工 |
| **16×32 KB ring** | 破坏 `(61440−1)+1500 < 65536` 安全界；除非把 `WIN_CAP` 降到 ≤31 KB（RTT 上限 24.8 µs，贴边 srtt 27 µs） |
| **C3（共享窗口池）** | 每口 24.6 KB ⇒ BDP 墙 19.7 µs；不省任何存储（信用不是存储） |
| **共享 16 槽动态重传池（单 retx）** | 两口 10G 同时写 ⇒ 需第二写口 ⇒ bank 翻倍 = 512 tile（>480） |
| **单栈加宽到 128 位跑 20G** | 全链数据面/MAC 都是 64 位；宽化 = 重写整条流水 + 两个 MAC 仍要分开，**不比双栈便宜** |
| **单口两 bitfile 各跑一半** | 不满足"同时" |
